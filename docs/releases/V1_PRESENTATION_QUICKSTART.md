# FleetLuma v1 classroom demo — operator quickstart

**Status (2026-11-23): paired cloud demo is deployed; final release still requires physical-host acceptance and signing.** The GitHub Windows/Linux installer candidates pass isolated CI. The live API passed health, protected operator-route, and synthetic create/cancel pairing checks. Real device approval and metric reporting through a freshly installed agent still require a presentation-machine test.

## What the presenter needs

- An operator-approved FleetLuma Supabase Auth account (do not create public signups).
- Working API at `https://fleetluma-api.vercel.app` (preview-configured deployment behind stable alias; pairing and workspace enforcement enabled).
- Flutter Web at `https://fleetluma-web.vercel.app` (dark pairing-enabled preview build assigned to stable alias after CI auth preflight).
- A physical Windows 11 machine for the installed background service demonstration. A second Linux machine is optional for the class demo, but required for the full cross-platform release sign-off.
- A network route from the installed agent to the configured **HTTPS API origin**.

## Windows agent: proposed user flow

1. From a reviewed GitHub Actions run, download the `fleetluma-windows-unsigned-installer` artifact and extract the .exe. For the 2026-11-23 candidate: https://github.com/Adam-BArbia/fleetluma/actions/runs/45141323996
2. Install with administrator confirmation. The installer registers and starts the `FleetLumaAgent` Windows background service; no system Python installation is needed. Developer candidate may produce Windows SmartScreen warnings because it is unsigned: do not ask users to bypass warnings for an unknown or unverified file.
3. Open **FleetLuma Agent Setup** (installer opens it after successful interactive installation) and choose **Start pairing**. The code is generated by the *agent*, not the web dashboard.
4. Choose **Open FleetLuma dashboard** or open the trusted operator site, sign in, then select **Manage devices**. Enter the displayed code, inspect hostname/OS/capabilities and approve only the machine you control.
5. Wait for the service to collect and report CPU, RAM and disk metrics. Refresh dashboard to observe CONNECTED and later STALE when the service is stopped. Historical readings must never be labeled live.
6. Test reboot/restart and revocation. Revoking must prevent further reports and require a fresh pairing; do not reuse an old bearer token.

## Linux agent: candidate

The unsigned Ubuntu/Debian package candidate with new interactive setup helper is available at https://github.com/Adam-BArbia/fleetluma/actions/runs/45143131797. Install the `.deb` with administrator privileges, then run `sudo fleetluma-setup` and answer `y` to request a code. The dedicated systemd service starts automatically, while the CLI guides you through approval at `https://fleetluma-web.vercel.app`. There is **no Linux graphical installer yet**. Validate package/reboot/pairing/purge on a physical host before claiming general plug-and-play support.

## Five-minute live presentation

1. Log in to Flutter Web and show the dark fleet overview and real sampled CPU/RAM/disk for the already enrolled demonstration host.
2. Show the agent installer and setup window on the second computer.
3. Pair with a code through Manage devices, approve the correct machine, then observe it appear in the dashboard.
4. Stop the agent briefly: explain the STALE status and preserved last-known readings. Restart to show recovery.
5. Revoke only the *new test agent*, demonstrating that a revoked credential cannot continue reporting; leave the existing TUFFEST pilot intact.

## Fail-closed presentation gates

- The live application MUST NOT claim that pairing is available when `FLEETLUMA_PAIRING_ENABLED` or `FLEETLUMA_PAIRING_UI_ENABLED` is off.
- Do not edit the existing TUFFEST identity, replace sample data, disable authorization or turn on wildcard CORS for the sake of a demo.
- If live pairing is not ready, demonstrate the previously enrolled monitoring host and show the installer/agent pairing UI as a candidate, explicitly identifying what has not been activated.
- Check backup/restore readiness, authenticated operator scope and exact API/Web deployment URLs before enabling pairing in a separate preview.
- Do not tag or distribute a signed v1 release until physical Windows/Linux acceptance, rollback and code-signing requirements pass. The authoritative activation checklist is `docs/releases/PAIRING_ACTIVATION_RUNBOOK.md`.
