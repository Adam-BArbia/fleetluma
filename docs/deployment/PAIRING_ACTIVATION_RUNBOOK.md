## 2. Preconditions before enabling public HTTPS pairing

1. Review source commit on `main` and all required CI checks.
2. Verify a full, independently restorable Supabase database backup and point-in-time recovery capability. Before activation, document who owns restoration; the additive migration is already applied and is **not** safely reversed by dropping workspace columns.
3. Review Supabase owner/workspace mapping and verify original host IDs, token hashes, sample counts and privileges using **aggregate/read-only SQL**; do not print tokens or raw hashes.
4. Make sure API preview and Flutter preview both use the same audited coordinator origin. Verify API's actual deployment URL and CORS origin. `fleetluma-web.vercel.app` may be aliased to a preview build; check current target before changing aliases.
5. Ensure remote operator JWT validation, exact CORS allowlist, per-device digest authentication, workspace scoping, rate limiting and revoke handling remain enabled. No public signup.
6. Generate a unique high-entropy `FLEETLUMA_PAIRING_PEPPER` in a trusted environment. Enter it directly as a masked Vercel API **preview** secret. Do not store it in a public GitHub variable, chat, logs or Flutter.
7. Enable `FLEETLUMA_PAIRING_ENABLED=true` and `FLEETLUMA_WORKSPACE_ENFORCEMENT_ENABLED=true` only in the reviewed API **preview** deployment, alongside its existing cloud configuration and private PostgreSQL URI. Keep both off in any unreviewed/public deployment.
8. Re-deploy the API preview and verify `/health` returns 200, unauthorized `GET /api/v1/operator/workspaces` returns 401, invalid agent credentials return 401 and all pairing responses omit private token material from public operator routes.
9. Deploy Flutter Web using the manually protected `FleetLuma cloud Web preview` workflow on reviewed `main`, with `enable_pairing_ui=true`. That build refuses to enable pairing unless the API's operator workspace endpoint responds 401 without a JWT.
10. Pair a **new test machine**. Do not revoke, rotate or overwrite TUFFEST's legacy agent credential until the new path is proven.

## 3. Full hardware acceptance checklist

- [ ] Native Windows installer on a clean Windows 11 machine; UAC elevation is explicit, service runs after reboot, protected setup window opens without a Python installation.
- [ ] Windows setup shows a code generated by the installed background service, not a manually supplied bearer token.
- [ ] Authenticated operator opens `/devices/pair` or Manage devices and reviews hostname, OS, capabilities and expiry before approval.
- [ ] Code expires after 10 minutes; wrong, denied and cancelled codes never enroll. Repeated polling is throttled.
- [ ] Approved agent persists its device identity under Windows DPAPI bound to the service identity; regular users cannot read the credential.
- [ ] Metrics appear and state becomes CONNECTED; after agent stop, status becomes STALE without erasing historical readings.
- [ ] Revocation immediately rejects future reports and never updates `last_seen_at` or samples; old credential cannot be used again.
- [ ] Agent restart, network outage, reboot, service stop/start, UI close and repeated pairing are tested.
- [ ] Same acceptance on Linux systemd with a dedicated `fleetluma` service UID and 0700/0600 storage and control socket.
- [ ] Windows upgrade, uninstall, reinstall and explicit repair paths pass; uninstaller leaves no credential.
- [ ] Static Web on mobile and desktop works with authenticated operator, renewal, logout and inaccessible workspaces.
- [ ] Installed package signatures/provenance and release checksums are established before general distribution.

## 4. Rollback strategy

**Application rollback is not schema rollback.** The migrated workspace columns and private pairing tables may remain when the flags are disabled.

- API: set `FLEETLUMA_PAIRING_ENABLED=false` and `FLEETLUMA_WORKSPACE_ENFORCEMENT_ENABLED=false` in its reviewed target and redeploy the last known working API. Verify `/health` 200. If a deployment was explicitly promoted, restore its last known good alias through Vercel deployment controls.
- Web: publish the last working cloud build with `FLEETLUMA_PAIRING_UI_ENABLED=false` or restore its alias to the previously tested build.
- Agents: stop only the test agent; keep the existing TUFFEST pilot untouched. Do not run a destructive token rotation or database restore to merely disable the UI.
- If you suspect credential compromise, revoke **that** enrolled host through an audited operator action and then repair it by pairing again.
- Repeat aggregate SQL verification for preserved TUFFEST host and sample counts; check operator login and stale/connected semantics.
